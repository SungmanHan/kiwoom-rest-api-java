# 키움 REST API Java 연동 5편 — 현재가·호가 조회부터 분봉·일봉·주봉·월봉까지

지난 편까지 앱키 발급과 Access Token 발급, 첫 API 호출을 다뤘습니다. 이번 5편에서는 실제로 화면·로직에 가장 많이 쓰는 시세 조회 4종 — 현재가(`ka10001`), 10단 호가(`ka10004`), 분봉·일봉·주봉·월봉(`ka10080`~`ka10083`) — 을 다룹니다. 응답 구조를 안다고 끝이 아니라, **부호가 붙은 숫자와 정렬 순서를 어떻게 파싱하느냐**가 실제로 버그가 나는 지점입니다.

## 이번 글에서 배울 것

- `ka10001` 한 번 호출로 현재가·52주 고저·시가총액·재무지표까지 받는 법
- `ka10004` 10단 호가 응답이 `LIST` 없이 root 필드 60여 개로 오는 구조와, 1차·2~5차 호가의 키 패턴 차이
- `ka10080`(분봉) / `ka10081`(일봉) / `ka10082`(주봉) / `ka10083`(월봉)의 공통 요청 파라미터와 필수 옵션
- 응답에 섞여 있는 부호 접두사(`+`/`-`)와 정렬 순서(최신이 먼저)를 안전하게 처리하는 방법

## 실제 코드 살펴보기

### ka10001 — 기본정보 / 현재가

요청은 `stk_cd`에 종목코드만 넣으면 됩니다. 정규장 종가가 아니라 시간외(NXT) 체결가가 필요하면 `_AL` 접미사를 붙입니다.

```java
Map.of("stk_cd", "005930")        // KRX
Map.of("stk_cd", "005930_AL")     // KRX+NXT 통합 (시간외 실거래가)
```

한 번 호출로 가격·등락·거래량·52주·시가총액·재무지표가 전부 옵니다.

| 분류 | 필드 |
|---|---|
| 가격 | `cur_prc`, `base_pric`, `open_pric`, `high_pric`, `low_pric`, `upl_pric`(상한), `lst_pric`(하한) |
| 등락 | `flu_rt`, `pred_pre`, `pre_sig` |
| 거래 | `trde_qty`, `acc_trde_qty`, `trde_pre` |
| 52주 | `250hgst`, `250lwst`, `250hgst_pric_dt`, `250hgst_pric_pre_rt` |
| 시총·주식 | `mac`(억원), `flo_stk`, `dstr_stk`(천주), `dstr_rt`, `for_exh_rt` |
| 재무 | `per`, `pbr`, `roe`, `eps`, `bps` |

재무 지표(`per`/`pbr`/`roe`/`eps`/`bps`)는 외부 벤더가 주 1회 갱신합니다. 실시간 값이 아니라는 점을 화면이나 알림 문구에 반영해 두는 게 좋습니다.

`_AL` 접미사는 호출 시점마다 다시 판단하지 말고, 배치 진입 시 한 번 결정해서 쓰는 편이 안전합니다.

```java
final String sfx = afterHoursSuffix && !resolveStexTp().equals("1") ? "_AL" : "";
```

그리고 결과를 `Map<String, ...>`에 담을 때 key는 반드시 plain 코드(`005930`)를 씁니다. `_AL`이 붙은 문자열을 그대로 key로 쓰면 이후 조회에서 전부 미스가 납니다.

### ka10004 — 10단 호가

호가는 1차와 2~5차의 필드 이름 패턴이 다릅니다.

```
매수 1차 : buy_fpr_bid      / buy_fpr_req
매수 2~5차: buy_2th_pre_bid  / buy_2th_pre_req   …  buy_5th_pre_bid
매도 1차 : sel_fpr_bid      / sel_fpr_req
매도 2~5차: sel_2th_pre_bid  / sel_2th_pre_req   …
총잔량   : tot_buy_req / tot_sel_req
기준시각 : bid_req_base_tm
```

애프터마켓(저녁 시간대)에는 `tot_buy_req` / `tot_sel_req`가 0으로 옵니다. 이때는 `ovt_buy_req` / `ovt_sel_req`로 폴백해야 합니다.

```java
long regular = Math.abs(parse(resp.path("tot_buy_req")));
return regular > 0 ? regular : Math.abs(parse(resp.path("ovt_buy_req")));
```

거래소 구분은 `stex_tp` 파라미터가 아니라 `stk_cd` 접미사로만 고릅니다. `_AL`로 바꾸면 호가 깊이가 늘어나므로, 잔량 임계값을 코드에 쓰고 있다면 재캘리브레이션이 먼저 필요합니다.

### ka10080~83 — 분봉 / 일봉 / 주봉 / 월봉

네 TR 모두 같은 엔드포인트(`/api/dostk/chart`)를 쓰고, 전부 `stk_cd` 접미사 방식입니다(`stex_tp` 파라미터 없음).

```java
// 분봉
Map.of("stk_cd", code, "tic_scope", "1", "upd_stkpc_tp", "1")

// 일 / 주 / 월봉
Map.of("stk_cd", code, "base_dt", "20260811", "upd_stkpc_tp", "1")
```

`upd_stkpc_tp="1"`(수정주가)는 필수입니다. 문서에 나오는 `updn_tp`는 미지원 파라미터라 이걸 보내면 원하는 결과가 오지 않습니다. 수정주가를 켜지 않으면 액면분할·유상증자 구간에서 캔들이 튀어 이동평균·박스권 계산이 깨집니다.

LIST 키는 TR마다 다릅니다.

| TR | 봉 | LIST 키 |
|---|---|---|
| `ka10080` | 분봉(`tic_scope`=1/5/15/…) | `stk_min_pole_chart_qry` 또는 `stk_mnt_pole_chart_qry` |
| `ka10081` | 일봉 | `stk_dt_pole_chart_qry` |
| `ka10082` | 주봉 | (동일 패턴) |
| `ka10083` | 월봉 | (동일 패턴) |

`ka10082`(주봉)·`ka10083`(월봉)은 재료에 "동일 패턴"이라고만 되어 있고 정확한 LIST 키 이름이 명시돼 있지 않습니다. 실제 구현 시에는 응답을 한 번 찍어 키 이름을 확인이 필요합니다.

전체 코드: [https://github.com/SungmanHan/kiwoom-rest-api-java/tree/main/quote](https://github.com/SungmanHan/kiwoom-rest-api-java/tree/main/quote) (현재가·호가), `chart/` 디렉터리(분·일·주·월봉)는 같은 저장소 상대경로로 확인할 수 있습니다.

## 코드 한 부분씩 설명

**정렬 안전장치.** 차트 응답은 최신 데이터가 `rows[0]`으로 오는 내림차순이 기본입니다. 이 전제가 깨지면 이동평균이 조용히 반대로 계산되는데, 예외조차 나지 않기 때문에 명시적으로 체크해야 합니다.

```java
if (candles.getFirst().date().isBefore(candles.getLast().date())) {
    log.warn("정렬 오름차순 감지 — reverse 적용");
    return new ArrayList<>(candles.reversed());
}
```

여기서 핵심은 "조용히 고치지 않는 것"입니다. `reverse()`만 적용하고 로그를 안 남기면, 나중에 실제로 정렬이 깨지는 원인이 생겨도 알아챌 방법이 없습니다.

**`limit(N)` 방향 실수.** `reverse()`로 오래된→최신 순으로 바꾼 뒤 `limit(5)`를 걸면 가장 오래된 5개가 나옵니다. 최근 5개가 필요하면 `subList(size-5, size)`를 써야 합니다.

**애프터마켓 봉 컷.** 분봉을 `_AL`(통합)로 받으면 NXT 애프터마켓 체결이 정규장 봉 뒤에 이어 붙습니다. VWAP·종가 같은 정규장 기준 지표를 계산한다면 15:30 이후 봉을 걸러내야 합니다.

```java
bars.stream().filter(b -> !b.time().isAfter(day.atTime(LocalTime.of(15, 30)))).toList();
```

이 필터는 "세션을 이렇게 정의한다"는 뜻이 아니라 재실행 오염을 막는 가드입니다. 조회 계층에는 필터를 걸지 않고, 계산 시점에만 적용하는 편이 나중에 프리마켓 용도로 재사용할 때 유리합니다.

## 여기서 주의해야 할 점

**ka10004에는 LIST가 없습니다.** 다른 TR처럼 배열로 감싸져 오지 않고, root 직속으로 60~71개 필드가 그대로 옵니다. 게다가 1차 호가(`sel_fpr_bid`)와 2~5차 호가(`sel_2th_pre_bid`)의 키 이름 패턴 자체가 다릅니다. `LIST` 파싱 코드를 재사용하려다 이 구조 차이를 놓치기 쉬운 지점입니다.

그 외 실제로 부딪히는 함정들:

- **저녁엔 총잔량이 0** — `tot_buy_req`/`tot_sel_req`는 애프터마켓에 0으로 오므로 `ovt_buy_req`/`ovt_sel_req`로 폴백해야 합니다.
- **`stex_tp`가 없다** — ka10004는 거래소를 `stk_cd` 접미사로만 고릅니다. `_AL`로 바꾸면 호가 깊이가 늘어나니 잔량 임계값을 쓰는 로직은 재캘리브레이션이 먼저입니다.
- **`_AL` 결과의 Map key는 plain 코드로** — `_AL`이 붙은 문자열을 key로 저장하면 이후 조회가 전부 미스납니다.
- **`updn_tp`는 미지원** — 차트 계열은 `upd_stkpc_tp="1"`을 반드시 보내야 하고, 문서에 나오는 `updn_tp`를 보내면 원하는 결과가 오지 않습니다.
- **정렬이 뒤집혀 오면 조용히 틀린다** — 최신이 `rows[0]`이라는 전제가 깨지면 예외 없이 이동평균이 반대로 계산됩니다. 안전장치를 걸고 로그를 남겨야 원인을 추적할 수 있습니다.
- **`_AL` 분봉엔 애프터마켓 봉이 섞인다** — 정규장 기준 지표를 계산한다면 15:30 이후 봉을 잘라내야 하고, 특히 장 마감 후 재실행 시 같은 코드가 다른 결과를 낼 수 있습니다.
- **부호·음수 표기가 TR마다 다르다** — 분봉은 `cur_prc`에 부호가 붙고 일봉은 안 붙습니다. `tot_sel_req_jub_pre`처럼 `--47` 식 이중 대시 음수도 있습니다.

## 직접 해보기

1. 보유 종목코드 하나로 `ka10001`을 호출해 `cur_prc`, `flu_rt`, `mac`을 출력해 봅니다. 부호를 제거하고 숫자로 변환하는 유틸이 제대로 동작하는지 확인합니다.
2. 같은 종목으로 `ka10004`를 호출해 `buy_fpr_bid`/`sel_fpr_bid`(1차)와 `buy_2th_pre_bid`/`sel_2th_pre_bid`(2차)를 함께 출력해 키 패턴 차이를 직접 눈으로 확인합니다.
3. 정규장 마감 후에는 `tot_buy_req`가 0으로 오는지, `ovt_buy_req`에 값이 들어오는지 비교해 봅니다.
4. `ka10081`을 호출해 받은 배열의 첫 번째와 마지막 `dt`를 비교해 실제로 내림차순인지 확인합니다.

## 이번 글 정리

- `ka10001`은 현재가·52주·시총·재무를 한 번에 주는 대신, 재무 지표는 주 1회 갱신이라는 한계가 있습니다.
- `ka10004`는 LIST 없이 root 필드로 오는 특수한 구조이고, 1차와 2~5차 호가의 키 패턴이 다릅니다.
- `ka10080`~`ka10083`은 같은 엔드포인트·같은 파라미터 규칙(`upd_stkpc_tp="1"` 필수)을 공유하지만 LIST 키 이름은 TR마다 다릅니다.
- 부호 접두사와 정렬 순서는 TR·봉 종류마다 미묘하게 달라서, 파서를 재사용할 때 가장 먼저 깨지는 지점입니다.
